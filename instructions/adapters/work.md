# Work

По умолчанию Work выполняет один короткий подготовительный проход, не исполняет оркестрацию пакета и передаёт его в Kimi Code. Бюджет подготовки: одно стартовое согласование, одна детерминированная проверка и не более 15 минут. Если данных недостаточно, задать конкретный вопрос вместо продолжительных исследований.

## Session defaults

При запуске задачи пользователь выбирает model и effort сессии. Названия Work сопоставляются как `Standard -> low`, `Advanced -> high`, `Extreme -> max`.

Эти session defaults управляют созданием и исполнением пакета и применяются ко всем субагентам, включая verifier и `package_checker`. В `execution.session_defaults` зафиксировать фактические `model` и `effort`. Каждая задача schema 3 всё равно содержит `model`, `effort`, `reason` и `assignment_source: work_session_default`; значения отражают пользовательский override и могут быть одинаковыми.

Session default Work имеет приоритет над фиксированным высоким назначением verifier из примера Code-профиля. Пользовательский выбор не требует discretionary model review. Нельзя утверждать, что Work поддерживает разные session effort у отдельных субагентов внутри одной сессии: подтверждена только настройка всей сессии.

## Подготовка пакета

1. Восстановить исходную задачу, ожидаемый результат, ограничения и критерии приёмки.
2. Показать стартовое согласование, включая уровень проверки, маршрут, team по умолчанию или явный solo, исполнителей, verifier, `package_checker`, model reviewer при необходимости, swarm, `max_parallel` и содержательные чек-поинты.
3. Создать компактный schema 3 пакет из шаблона без детального плана реализации. До проверки заполнить DAG, назначения моделей и SHA-256 активного профиля. Применить Work session defaults ко всем задачам.
4. Только после согласования установить `execution.implementation_authorized: true`, заполнить `execution.approval` и записать `стартовое согласование пользователя` в `RUN_LOG.md`. Solo требует отдельной записи явного выбора пользователя.
5. Поручить отдельному субагенту `package_checker` запустить общий валидатор с теми же session defaults. Координатор передаёт обязательный `validator_path`, то есть фактический абсолютный путь к `scripts/validate_package.py` от корня установленного навыка, и абсолютный путь пакета. Он сохраняет команду, код выхода, stdout, stderr, JSON-результат, `package_revision` и доступный ID вызова. Субагент не исправляет пакет и не изменяет вердикт.
6. При успешной проверке установить `ready_for_kimi_code` или `ready_for_work`. После изменения статических входов или YAML-профиля проверка становится `stale`, повторяет её новый экземпляр `package_checker`.

Без разрешения на проверяющего субагента пакет можно исправлять, но он остаётся `package_check_pending`. Независимая проверка пакета выполняется только по отдельному явному запросу пользователя, не заменяет детерминированную проверку и не относится к качеству будущего продукта.

## Явный выбор исполнения в Work

Work может предложить `execution.owner: kimi_work`, только если задачу целесообразно выполнить в текущей среде. В одном явном вопросе указать причину, генераторов, verifier, `package_checker`, model reviewer при необходимости, возможный swarm, `max_parallel` и ожидаемую экономию контекста. Пользователь может выбрать маршрут Code без дополнительного обоснования. Молчаливый выбор Work или solo запрещён.

Подтверждение разрешает только перечисленные роли и параллельность. Согласие на независимую проверку не разрешает генераторов. Новая роль или увеличение параллельности требуют нового вопроса.

После выбора Work:

1. Сохранить цель, объём, критерии и обязательные доказательства без сокращения.
2. Установить `execution.stop_policy: cooperative`, провести pre-flight и начать без повторного подтверждения запуска. Проверить доступность выбранных session model и effort; скрытый fallback запрещён.
3. В team координировать, не выполняя содержательную генерацию в основной сессии. Согласованные субагенты создают результат, отдельный субагент проверяет его. В явно выбранном solo основная сессия может создавать результат, verifier остаётся отдельным.
4. Передавать каждому субагенту только карточку, необходимые входы, ограничения, session defaults и пути выходов. Хранить подробные доказательства в файлах.
5. Использовать swarm только для независимых веток в пределах разрешения. По умолчанию `max_parallel: 1`. При недоступности выполнить последовательный запуск тех же ролей и записать причину, не подменяя модель или режим.
6. До каждого вызова сохранять намерение и ожидаемые выходы, использовать атомарную замену итоговых файлов и поддерживаемые таймауты команд.
7. Если контекст исчерпан, остановиться и явно предложить Code или разбиение. Не уменьшать задачу молча.

## Остановка и восстановление

Команду пользователя, полученную между завершёнными вызовами, выполнить как контролируемую остановку: не запускать новые ветки, записать причину, последнюю операцию и фактические выходы, отметить черновики и установить `cancelled`.

Активный foreground вызов нельзя считать отменённым или проведённым до безопасной границы без подтверждённой возможности среды. После прерывания клиентом сверить журнал, файлы и следы последнего вызова. Если завершение и целостность не подтверждены, установить `interrupted` и запросить решение о новом запуске, продолжении или отмене. Автоматическое продолжение запрещено.

В подготовительном маршруте Work по-прежнему запрещено писать или отлаживать реализацию, тесты и валидаторы продукта, исследовать среду Code и создавать детальный план за него. Не сообщать о выполнении или проверке продукта без фактических доказательств.
