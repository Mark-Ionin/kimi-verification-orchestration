# Запуск

## Предусловия

- Пакет имеет статус `ready_for_kimi_code` или `ready_for_work` и успешную детерминированную проверку отдельного `package_checker`.
- Пользователь дал одно стартовое согласование, подтверждённое `execution.approval` и записью в `RUN_LOG.md`.
- Исполнительные субагенты, verifier, `package_checker`, model reviewer при необходимости, swarm и параллельность согласованы раздельно в пределах одного стартового вопроса. Коммиты, публикация, установка и необратимые действия требуют отдельных разрешений.
- Schema 3 использует `team` по умолчанию. `solo` выбран пользователем явно и записан в `RUN_LOG.md`.
- Для `kimi_work` явно согласованы маршрут и роли, установлен `execution.stop_policy: cooperative`, session defaults применены ко всем задачам и субагентам.

## Новая сессия Code

Создающая Code-сессия не исполняет пакет. После успешной проверки пользователь вручную запускает новую основную Code-сессию:

```bash
cd "<absolute-package-parent>" && kimi
```

Для маршрута Work пакет открывается в явно выбранной пользователем сессии Work.

## Первое сообщение

Прочти `00_ORCHESTRATOR.md`, `MANIFEST.yaml`, активный YAML-профиль и `verification/PLAN.md`. Проведи pre-flight и сохрани `verification/PREFLIGHT.json`. Проверь фактическую доступность model, effort и runtime_alias каждой задачи. Недоступность назначения является блокером, скрытый fallback запрещён, замена требует пересогласования.

До исполнения получи review discretionary high и max. Если критических блокеров нет, сразу выполни основную работу и проверки, сохраняя фактические доказательства в `RUN_LOG.md`. Не останавливайся после pre-flight для повторного подтверждения запуска.

В team основная сессия только оркестрирует содержательную генерацию согласованных субагентов. Запускай только согласованные роли, назначенные runtime aliases и параллельность. В solo работу может вести основная сессия, но независимый verifier остаётся отдельным субагентом.

Согласие на независимую проверку разрешает только её субагента и `package_checker`. Не используй свежую сессию вместо verifier. После исправления `P0` или `P1` назначь новый экземпляр verifier. После неудачной задачи эскалацию model или effort записывай с причиной; discretionary high или max повторно проходит review.

В Work применяй session defaults ко всем субагентам, включая verifier и `package_checker`. Сохраняй компактный файловый контекст, используй последовательное исполнение при недоступности swarm, останавливай новые ветки по команде между завершёнными вызовами и устанавливай `cancelled`. После прерывания с неподтверждённой целостностью установи `interrupted` и запроси решение пользователя, не продолжая автоматически. Не обещай отмену активного foreground вызова.

Если независимый verifier недоступен, заверши реализацию со статусом `verification_pending`.
