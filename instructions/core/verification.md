# Верификация

## Выбор

- `Нет`: простая низкорисковая задача, отдельный верификатор не требуется.
- `Малая`: один профиль `М1–М5`.
- `Полная`: малый профиль и один или несколько профилей `П1–П14`.

Оценить сложность, цену ошибки, источники, преобразования данных и последствия. Перед полной проверкой назвать профили и обосновать риск на стартовом согласовании. Состав профилей читать из `../registries/verification-profiles.yaml`.

Проверка должна быть пропорциональна риску и не заменять основную реализацию. По умолчанию проверяется фактический результат, а не пакет оркестрации.

## Независимость

Верификатор получает исходную задачу, фактический результат, критерии, источники и воспроизводимые доказательства. Он не генерирует и не исправляет результат и не использует объяснения генератора как источник истины.

В Kimi Code и Kimi Work включённая независимая проверка выполняется только отдельным субагентом, не участвовавшим в генерации. Вопрос о включении проверки одновременно запрашивает разрешение на её субагента, но не разрешает исполнительных субагентов или swarm. Без разрешения основная реализация продолжается и завершается как `verification_pending`. Свежая сессия, самопроверка и декларация не являются заменой субагента.

После исправления `P0` или `P1` назначать новый экземпляр субагента-верификатора. Для полной или многоитерационной проверки применять `П14`: diff, повтор применимых механизмов, регрессию и контроль дрейфа смысла. Для малой проверки повторить малый профиль и проверить diff.

Детерминированную проверку пакета в Code и Work выполняет отдельный `package_checker`, запускающий общий валидатор и сохраняющий фактический след. Независимая смысловая проверка пакета выполняется только по отдельному явному запросу и не относится к качеству будущего продукта. Для schema 3 `package_revision` также включает YAML-профиль моделей и его SHA-256.

## Замечания

- `P0`: результат неверен, опасен или непригоден.
- `P1`: нарушен обязательный критерий или гейт.
- `P2`: локальное улучшение без нарушения требований в проверенном контексте.

`P0` и `P1` блокируют готовность. После исправления требуется повторная проверка. При изменении среды, входов или границ применения заново оценить критичность открытых `P2`: замечание может стать блокирующим.

При защитном снимке исходников включать все предсуществующие файлы. Исключать только подтверждённые новые выходы и явно согласованные служебные каталоги, не исключая автоматически `tools/` или `tests/`. Для символических ссылок сохранять путь, цель и доступные метаданные, а не пропускать их.

## Отчёт и ревизия

Для каждой проверки записать: требование, профиль, механизм, метод, доказательство, результат, критичность. Отдельно указать непроверенное, ограничения и остаточные риски. Допустимые доказательства: наблюдение, вывод скрипта, diff, сверка с источником или иной воспроизводимый след.

В `verification/REPORT.md` для схем 2 и 3 добавить YAML front matter:

```yaml
---
independent: true
verifier_agent: "A3"
invocation_id: "<реальный-id-вызова>"
criteria_revision: "<sha256>"
result_revision: "<sha256>"
result_files:
  result.md: "<sha256>"
previous_report: null
snapshot: null
diff: null
open_p0: 0
open_p1: 0
open_p2: 0
---
```

В `result_files` включать все проверенные файлы результата, кроме журналов и отчётов, и записывать SHA-256 каждого файла. `result_revision` вычислять как SHA-256 канонического JSON-словаря `result_files` с сортировкой ключей, `ensure_ascii=false` и компактными разделителями.

`criteria_revision` вычислять как SHA-256 канонического JSON со следующей точной структурой, с сортировкой ключей, `ensure_ascii=false` и компактными разделителями:

```json
{
  "scope": {
    "objective": "<scope.objective>",
    "acceptance_criteria": []
  },
  "implementation_scope": "<implementation.scope>",
  "verification": {
    "enabled": true,
    "level": "<verification.level>",
    "small_profile": "<verification.small_profile>",
    "full_profiles": []
  }
}
```

Значения брать из `MANIFEST.yaml`, копируя `scope` целиком со всеми фактическими полями. Для вычисления `criteria_revision` использовать общий вычислитель по абсолютному пути: `python "<validator_path>" --criteria-revision "<absolute-package>"`, не подбирать хеш вручную. `validator_path` – обязательный фактический абсолютный путь к `scripts/validate_package.py` от корня установленного навыка, который координатор передаёт вместе с абсолютным путём пакета; разрешать путь от `cwd` пакета запрещено. Валидатор пересчитывает хеши и отклоняет отчёт при изменении результата или критериев.

Для каждой повторной проверки до исправления архивировать прежний `verification/REPORT.md` под уникальным неизменяемым именем и сохранять защитный байтовый snapshot всех файлов из прежнего `result_files` вместе с их SHA-256. Архив и snapshot не перезаписывать. Новый `REPORT.md` связывать с прежней проверкой через `previous_report`, а со старой и новой ревизиями через `snapshot` и `diff`, указывая пути к соответствующим артефактам. `verification/REPORT.md` остаётся отчётом последней проверки. Для первой проверки `previous_report`, `snapshot` и `diff` оставлять `null`; уже существующую историю не пересоздавать.

Отчёт должен быть достаточным для проверки, но не разрастаться за счёт пересказа пакета и хронологии подготовки. Основное место доказательств: фактические артефакты, тесты и `RUN_LOG.md` в Kimi Code.
